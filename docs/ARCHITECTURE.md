# هيكلة المشروع (Architecture Overview)

## طبقات الخادم الخلفي (Backend)

```
Controller → Service → Repository → Prisma → SQLite
```

- **Controller**: يستقبل الطلب، يتحقق من الصلاحيات، يستدعي الـ Service، يرجع الرد.
- **Service**: منطق العمل (business logic). لا يعرف شيئًا عن Express.
- **Repository**: الوصول الوحيد لقاعدة البيانات عبر Prisma.
- لا يوجد أي منطق قاعدة بيانات داخل Controller مباشرة — هذا مبدأ ثابت
  في كل الموديولات القادمة.

## طبقات الواجهة (Frontend)

```
Page → Component → Hook → Service (apiClient)
```

- كل صفحة تجارية جديدة تُبنى فوق `components/ui` الموجودة (Button, Input,
  Card, SummaryCard) بدل إعادة اختراعها.

## قاعدة البيانات

- SQLite عبر Prisma، مع تصميم يسمح مستقبلاً بالانتقال لـ PostgreSQL.
- في هذه المرحلة: جدولان فقط (`User`, `ApplicationSettings`) لإثبات أن
  الاتصال والـ migrations والـ seed تعمل. كل موديول تجاري يضيف جداوله
  الخاصة مع migration منفصلة عند بنائه — وليس دفعة واحدة.
- المبدأ الثابت للمراحل القادمة: أي رصيد مالي (دين، صندوق، مخزون) يُحسب
  من سجل حركات (transactions/movements)، لا يُخزَّن كرقم نهائي فقط.

## الأمان (ما هو مطبّق الآن، وما سيُبنى)

مطبّق الآن:
- Electron: `contextIsolation: true`, `nodeIntegration: false`, `sandbox: true`.
- Backend: Helmet، CORS محصور بالمنافذ المحلية، rate limiting أساسي على المصادقة.
- لا كلمات مرور أو أسرار مكتوبة داخل الكود؛ كل شيء عبر `.env` مع تحقّق Zod عند الإقلاع.

يُبنى في المرحلة 2 (الأمان):
- Argon2id لكلمات المرور، الجلسات، الأدوار، الصلاحيات، سجل التدقيق (Audit Log) الكامل.

## لماذا لا توجد كل الجداول/الموديولات الآن؟

بناء عشرات الجداول والموديولات دفعة واحدة بدون اختبار كل خطوة يؤدي عادة
لأخطاء مخفية يصعب تتبعها لاحقًا. المسار المتبع هنا: كل مرحلة تُبنى، تُختبر
فعليًا (`pnpm test`، فحص يدوي)، ثم تُعتمد قبل الانتقال للمرحلة التالية —
تمامًا كما هو موصوف في خطة التطوير الأصلية (11 مرحلة).
