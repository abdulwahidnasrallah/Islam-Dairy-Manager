# Islam Dairy Manager (IDM)
### إسلام للألبان والأجبان — نظام إدارة أعمال (ERP) للعمل بدون إنترنت

> **حالة المشروع: مكتمل — كل المراحل العشر منجزة + Final Polish.**
> نظام ERP حقيقي وشغّال بالكامل لمحل ألبان وأجبان: مصادقة حقيقية بأدوار
> وصلاحيات، موردون وشراء حليب، منتجات ومخزون وإنتاج، مبيعات وزبائن
> وديون (مع فواتير مرقّمة قابلة للطباعة وQR ورمز إلغاء آمن)، نظام مالي
> وصندوق وربح مبني على تكلفة كل منتج فعلياً (COGS)، تقارير وتحليلات،
> لوحة تحكم حقيقية، بحث موحّد، إغلاق يومي آمن، إعدادات حقيقية (بما فيها
> تنظيف بيانات التشغيل بضغطة زر آمنة لبدء العمل الحقيقي)، مساعد ذكي
> اختياري، ونسخ احتياطي/استعادة فعلي من داخل التطبيق. يعمل بالكامل بدون
> إنترنت (باستثناء المساعد الذكي، الذي يحتاج اتصالاً فقط عند استخدامه).
>
> **قبل التوزيع الفعلي كمُثبِّت Windows**، راجع قسم "قيود حقيقية" في
> `docs/ROADMAP.md` (Phase 9): بناء المُثبِّت النهائي يحتاج جهاز Windows
> حقيقي (لم يكن هذا متاحاً في بيئة كتابة الكود) بسبب اعتماديات أصلية
> (native modules) مثل `argon2`. تشغيل النظام نفسه عبر `pnpm dev` لا
> يتأثر بهذا القيد إطلاقاً — يعمل على أي جهاز فيه Node.js.
>
> **ملاحظة تحقق مهمة (مُحدَّثة بعد إصلاح SQLite/enum)**: `database/prisma/schema.prisma`
> كان يستخدم Prisma enums، وهذه غير مدعومة على SQLite ("the current
> connector does not support enums") — تم إصلاح هذا بالكامل: كل الحقول
> الثمانية التي كانت enum أصبحت `String` عادي (نفس القيم بالضبط)، مع
> الاعتماد على تحقق Zod الموجود أصلاً كطبقة التحقق الوحيدة (وهي كانت
> فعلياً طبقة التحقق الحقيقية لأي طلب HTTP من الأساس). أُنشئت أيضاً
> `database/prisma/migrations/20260814000000_init/migration.sql` يدوياً
> (لم يكن ممكناً تشغيل `prisma migrate dev` فعلياً — لا إنترنت في بيئة
> الكتابة) لكن **تم اختبارها فعلياً وتنفيذها بنجاح** ضد قاعدة بيانات
> SQLite حقيقية عبر وحدة `node:sqlite` المدمجة في Node 22 (وليس
> Prisma Client نفسه، لكنه تنفيذ SQL حقيقي لا مراجعة نظرية): كل الجداول
> الـ23 أُنشئت بنجاح، قيود المفاتيح الأجنبية والفريدة تعمل فعلياً
> (اختُبر الرفض الصحيح لإدخالات غير صالحة)، والقيم الافتراضية صحيحة.
> كما أُعيد تنفيذ منطق seed.ts بالكامل (الصلاحيات، الأدوار، الموردين،
> المنتجات، الفواتير المرقّمة تسلسلياً، المخزون المُشتق) كـ SQL خام ضد
> نفس القاعدة ونجح بالكامل. راجع قسم "التحقق من أن كل شيء يعمل فعليًا"
> أدناه للتفاصيل الكاملة، وقسم "إصلاح SQLite/Enum" في `docs/ROADMAP.md`.
>
> **ما لم يتغيّر**: لا يزال تشغيل `pnpm install` و `pnpm build` و
> `pnpm test` الفعليين عبر pnpm/tsc/vitest غير ممكن في بيئة الكتابة (لا
> إنترنت لتثبيت الحزم) — لكن الفحص البنيوي الدقيق لكل استيراد ونوع
> بيانات (Final Polish) + التنفيذ الفعلي لملف الـ migration والبيانات
> (هذا الإصلاح) يغطيان الجزءين الأكثر عرضة للخطأ. أول أمر بعد فك الضغط:
> `pnpm install && pnpm build`.
> راجع `docs/ROADMAP.md` لتفاصيل كل مرحلة.

## خطوات التشغيل (على جهازك — هذه البيئة هنا بدون إنترنت)

```bash
# 1) من جذر المشروع
cp .env.example .env

# 2) تثبيت كل الحزم لكل الـ workspaces
pnpm install

# 3) توليد Prisma Client وتطبيق قاعدة البيانات
# (migration أولية موجودة مسبقاً وتغطي كل المخطط الحالي بالكامل —
#  هذا الأمر يطبّقها فقط، لن يطلب اسم migration جديد لأنه لا يوجد
#  تغيير غير مُطبَّق)
pnpm db:generate
pnpm db:migrate

# 4) تعبئة بيانات أولية (مستخدم تجريبي admin / ChangeMe123!)
pnpm db:seed

# 5) شغّل الخادم الخلفي (نافذة طرفية منفصلة)
pnpm backend
# يجب أن يطبع: Islam Dairy Manager backend running on http://localhost:4000

# 6) شغّل الواجهة (نافذة طرفية أخرى)
pnpm frontend
# افتح المتصفح على http://localhost:5173

# 7) (اختياري) شغّل تطبيق سطح المكتب Electron
pnpm desktop
```

## التحقق من أن كل شيء يعمل فعليًا

1. `pnpm install` — يجب أن ينتهي بدون أخطاء (يثبّت التبعيات الجديدة من
   Final Polish: `@anthropic-ai/sdk`, `qrcode`, `html2canvas`، ويثبّت
   Prisma **5.22.0** بالضبط كما طُلب).
2. `pnpm db:generate` — يولّد Prisma Client. **لا حاجة لتشغيل
   `prisma migrate dev` لإنشاء migration جديد** — ملف
   `database/prisma/migrations/20260814000000_init/migration.sql`
   موجود مسبقاً ومُختبَر فعلياً (راجع "إصلاح SQLite/Enum" في
   `docs/ROADMAP.md`). شغّل `pnpm db:migrate` فقط لتطبيقه على قاعدة
   بياناتك المحلية (سيُنشئ `database/dev.db` ويطبّق الـ migration
   الموجود دون طلب migration جديد، لأن المخطط والملف متطابقان تماماً).
3. `pnpm build` — يجب أن يبني كل الحزم (`shared-*`, `backend`,
   `frontend`, `desktop`) بدون أخطاء TypeScript. **هذا أهم خطوة تحقق
   قبل الاستخدام** — راجع الملاحظة في أعلى الملف حول عدم القدرة على
   تشغيل هذا الأمر فعليًا في بيئة كتابة الكود.
4. `pnpm test` — يجب أن تنجح كل الاختبارات (أكثر من 15 ملف اختبار عبر
   كل الموديولات).
5. `pnpm db:seed` ثم افتح `http://localhost:4000/api/health` — يجب أن
   ترى `"status": "running"` و `"databaseConnected": true`.
6. سجّل دخول (admin / ChangeMe123!) وتأكد يدويًا من:
   - **لوحة التحكم**: أرقام حقيقية (ليست "—")، وزر "بدء يوم جديد" يعمل.
   - **الإعدادات**: تعديل اسم المتجر ثم الرجوع للوحة التحكم — الاسم
     الجديد يظهر في الترويسة فورًا.
   - **المبيعات**: سجّل فاتورة، افتحها من رقمها، تأكد من ظهور QR Code
     وأن زر "طباعة" و"تصدير PNG" يعملان، ثم جرّب "إلغاء الفاتورة" وتأكد
     أن المخزون يعود والدين يُصفَّر.
   - **البحث**: اكتب أي اسم زبون أو رقم فاتورة في شريط البحث بالأعلى
     وتأكد من ظهور نتائج قابلة للنقر.
   - **الإنتاج**: سجّل دفعة إنتاج فيها كمية حليب مستهلكة، ثم افتح
     المنتج وتأكد أن "سعر التكلفة" تحدَّث تلقائيًا.

## ما الذي **لم** يُبنى بعد (بالتصميم)

- لا شيء على مستوى الموديولات — كل المراحل العشر منجزة + Final Polish.
- القيد الأول: التحقق الفعلي من مُثبِّت Windows على جهاز Windows حقيقي
  (راجع "قيود حقيقية" في Phase 9 داخل `docs/ROADMAP.md`).
- القيد الثاني: `pnpm install`/`pnpm build` لم يُشغَّلا فعليًا في بيئة
  كتابة الكود (بدون إنترنت) — راجع الملاحظة أعلى هذا الملف.
- فجوة معروفة قديمة (من المرحلة 3 الأصلية، وليست جزءاً من Final
  Polish): صلاحية `manage_users` معرَّفة لكن لا توجد شاشة لإدارة
  المستخدمين تستخدمها — كل تعديل مستخدمين حاليًا يتم يدويًا عبر
  Prisma Studio (`pnpm db:studio`). لم تكن ضمن قائمة Final Polish
  المطلوبة، لذا لم تُبنَ الآن — موثّقة هنا للشفافية.

راجع `docs/ARCHITECTURE.md` و `docs/ROADMAP.md` للتفاصيل الكاملة.

## المرحلة 2: الموردون وشراء الحليب

### ما الذي أُضيف

- **قاعدة البيانات**: نماذج `Supplier`, `MilkPurchase`, `SupplierPayment` في `database/prisma/schema.prisma`.
- **Backend**: ثلاث موديولات كاملة بنفس الطبقات (Controller → Service → Repository):
  - `apps/backend/src/modules/suppliers/`
  - `apps/backend/src/modules/milk-purchases/`
  - `apps/backend/src/modules/supplier-payments/`
- **Frontend**: صفحات حقيقية تستخدم نفس مكونات Phase 1:
  - `/suppliers` (قائمة + بحث)
  - `/suppliers/new` و `/suppliers/:id/edit` (نموذج الإضافة/التعديل)
  - `/suppliers/:id` (ملف المورد: الرصيد، المشتريات، الدفعات، تسجيل دفعة)
  - `/milk-purchases` (تسجيل شراء + آخر العمليات)

### أوامر Prisma المطلوبة (بعد تعديل schema.prisma)

```bash
# من جذر المشروع
pnpm db:migrate --name add_supplier_and_milk_purchase
pnpm db:generate
pnpm db:seed   # يضيف مورد تجريبي "مزرعة الأمل" مع عملية شراء تجريبية
```

### طريقة التشغيل والاختبار

```bash
pnpm backend     # طرفية 1
pnpm frontend    # طرفية 2
```

1. سجّل دخول بأي اسم مستخدم (لا يزال وهميًا من Phase 1).
2. افتح **الموردون** من القائمة الجانبية — يجب أن تشاهد المورد التجريبي
   "مزرعة الأمل" مع رصيد مستحق قدره 50.
3. اضغط على اسم المورد → تحقق من ظهور المشتريات، إضافة دفعة (مثلاً 50)
   وتأكد أن الرصيد يصبح 0 فورًا.
4. افتح **شراء الحليب** من القائمة الجانبية، سجّل عملية شراء جديدة، وتأكد
   أن "القيمة الإجمالية" تُحسب تلقائيًا (الكمية × السعر) قبل الحفظ.
5. اختبارات الكود: `pnpm --filter backend test` — يتحقق من صحة معادلة
   الحساب (الإجمالي، المتبقي) ومن رفض دفعة أكبر من الإجمالي.

### قيود مقصودة في هذه المرحلة

- شراء الحليب **لا** يُحدّث المخزون أو الصندوق تلقائيًا بعد — هذا يتطلب
  وجود موديولي Inventory و Cash Register أولاً (المرحلتان 5 و 7). تم توضيح
  هذا كتعليق في `purchase.service.ts` حتى لا يُنسى.
- لا يوجد سجل حركات (ledger) منفصل؛ رصيد المورد يُحسب مباشرة من مجموع
  المشتريات ناقص مجموع المدفوعات — وهذا يطابق مبدأ "لا نخزّن رصيدًا نهائيًا
  فقط" لأن الرصيد يُشتق دائمًا من السجلات الفعلية.

## المرحلة 4: المنتجات والمخزون والإنتاج

### ما الذي أُضيف

- **قاعدة البيانات**: نماذج `Product`, `InventoryMovement`, `ProductionBatch`
  في `database/prisma/schema.prisma`.
- **Backend**: ثلاث موديولات كاملة بنفس الطبقات (Controller → Service → Repository):
  - `apps/backend/src/modules/products/`
  - `apps/backend/src/modules/inventory/`
  - `apps/backend/src/modules/production/`
- **Frontend**: صفحات حقيقية تستخدم نفس مكونات المراحل السابقة:
  - `/products` (قائمة + بحث + حذف) و `/products/new`, `/products/:id/edit`
  - `/inventory` (المخزون الحالي مع تنبيه انخفاض المخزون + تسجيل تعديل يدوي)
  - `/production` (تسجيل دفعة إنتاج + آخر الدفعات)

### أوامر Prisma المطلوبة (بعد تعديل schema.prisma)

```bash
# من جذر المشروع
pnpm db:migrate --name add_product_inventory_production
pnpm db:generate
pnpm db:seed   # يضيف منتج تجريبي "جبنة بيضاء" مع دفعة إنتاج تجريبية
```

### طريقة التشغيل والاختبار

```bash
pnpm backend     # طرفية 1
pnpm frontend    # طرفية 2
```

1. سجّل دخول (admin / ChangeMe123!).
2. افتح **المنتجات** من القائمة الجانبية — يجب أن تشاهد المنتج التجريبي
   "جبنة بيضاء".
3. افتح **الإنتاج**، سجّل دفعة إنتاج جديدة لأي منتج، وتأكد أن **المخزون**
   يرتفع بنفس الكمية فوراً بعد الحفظ.
4. افتح **المخزون**، جرّب تسجيل حركة "إخراج" بكمية أكبر من المتوفر فعلياً
   وتأكد من ظهور رسالة رفض بدلاً من قبول الحركة.
5. اختبارات الكود: `pnpm --filter backend test` — يتحقق من رفض إخراج
   مخزون أكبر من المتوفر ومن إنشاء حركة مخزون صحيحة مع كل دفعة إنتاج.

### قيود مقصودة في هذه المرحلة

- حقل "الحليب المستهلك" في دفعة الإنتاج رقم حر لأغراض التوثيق فقط، وغير
  مربوط بمخزون حليب خام فعلي بعد — ذلك يتطلب نموذج مخزون مواد خام منفصل.
- المبيعات لا تخصم من المخزون بعد (لأن موديول المبيعات لم يُبنَ بعد) —
  هذا يأتي في المرحلة 5.
- مثل رصيد المورد، مخزون كل منتج **لا يُخزَّن كرقم نهائي**؛ يُشتق دائمًا
  من مجموع حركات الإدخال ناقص الإخراج في `InventoryMovement`.

## المرحلة 5: المبيعات والزبائن والفواتير والديون

### ما الذي أُضيف

- **قاعدة البيانات**: نماذج `Customer`, `Invoice`, `InvoiceItem`,
  `CustomerPayment` + إضافة `SALE` إلى enum `InventoryMovementReason`.
- **Backend**: ثلاث موديولات كاملة بنفس الطبقات (Controller → Service → Repository):
  - `apps/backend/src/modules/customers/`
  - `apps/backend/src/modules/sales/` (فواتير البيع)
  - `apps/backend/src/modules/customer-payments/`
- **Frontend**:
  - `/customers` (قائمة + بحث)، `/customers/new`, `/customers/:id/edit`،
    و `/customers/:id` (ملف الزبون الكامل).
  - `/sales` — فاتورة بيع بعدة أصناف مع إضافة/حذف سطر ديناميكياً.
  - `/debts` — الزبائن الذين عليهم دين حالياً فقط.

### أوامر Prisma المطلوبة (بعد تعديل schema.prisma)

```bash
pnpm db:migrate --name add_sales_customers_invoices
pnpm db:generate
pnpm db:seed   # يضيف زبون تجريبي "بقالة الأمل" مع فاتورة بيع تجريبية
```

### طريقة التشغيل والاختبار

```bash
pnpm backend     # طرفية 1
pnpm frontend    # طرفية 2
```

1. سجّل دخول (admin / ChangeMe123!)، افتح **الزبائن** وتأكد من ظهور
   الزبون التجريبي "بقالة الأمل" بدين ظاهر.
2. افتح **المبيعات**، سجّل فاتورة جديدة لأي زبون ومنتج، وتأكد أن
   **المخزون** ينخفض بنفس الكمية فوراً بعد الحفظ.
3. جرّب بيع كمية أكبر من المتوفر فعلياً وتأكد من ظهور رسالة رفض بدلاً
   من قبول الفاتورة.
4. افتح **الديون** وتأكد من ظهور الزبائن الذين عليهم رصيد مستحق فقط.
5. اختبارات الكود: `pnpm --filter backend test` — يتحقق من حساب
   الإجمالي من الخادم، ورفض بيع كمية أكبر من المخزون، ورفض دفعة مقدَّمة
   أكبر من إجمالي الفاتورة.

### قيود مقصودة في هذه المرحلة

- لا يوجد بعد فواتير قابلة للطباعة/PDF — يأتي مع التقارير.
- لا يمكن تعديل أو حذف فاتورة بعد إنشائها؛ أي تصحيح لاحق يحتاج موديول
  "مرتجعات مبيعات" منفصل بدل تعديل مباشر، حفاظاً على مبدأ أن حركات
  المخزون سجل لا يُعدَّل ولا يُحذف.
- مثل رصيد المورد ومخزون المنتج، دين الزبون **لا يُخزَّن كرقم نهائي**؛
  يُشتق دائمًا من إجمالي الفواتير ناقص المدفوع (سواء عند الفاتورة أو
  كدفعة منفصلة).

## المرحلة 6: النظام المالي (مصاريف، صندوق، أرباح)

### ما الذي أُضيف

- **قاعدة البيانات**: نماذج `Expense`, `CashAdjustment`.
- **Backend**:
  - `apps/backend/src/modules/expenses/` — CRUD مصاريف.

## Final Polish: إكمال النواقص (بعد المرحلة 10)

بعد اكتمال كل المراحل العشر الأصلية، طُلب "Final Polish" لإكمال ميزات
كانت موجودة جزئيًا أو مفقودة. كل ما يلي كود حقيقي متصل بقاعدة البيانات
فعليًا — لا واجهات بدون منطق خلفي، ولا بيانات وهمية.

### 1. لوحة التحكم (Dashboard) — بيانات حقيقية بالكامل

استُبدلت كل الأرقام الوهمية بموديول `apps/backend/src/modules/dashboard/`
الذي يجمّع بيانات حقيقية من نفس الخدمات التي تستخدمها بقية الصفحات
(لا تكرار منطق، فلا يمكن أن تُظهر اللوحة رقمًا مختلفًا عمّا تراه في
صفحة الصندوق أو الديون أو المخزون نفسها):

- مبيعات اليوم، أرباح اليوم (COGS-based)، النقد الموجود، ديون الزبائن،
  مستحقات الموردين، قيمة المخزون، عدد المنتجات منخفضة المخزون، وملخص
  مبيعات اليوم (نقدي مقابل دين).
- تتحدّث تلقائيًا كل 60 ثانية، وفورًا عند فتح الصفحة.

### 2. الإعدادات (Settings) — صفحة حقيقية متصلة بقاعدة البيانات

`apps/backend/src/modules/settings/` يدير جدول `ApplicationSettings`
(كان موجودًا مسبقًا لكن غير مُستخدَم فعليًا). تشمل الإعدادات: اسم
المتجر، الهاتف، العنوان، العملة، بادئة رقم الفاتورة، ملاحظة الفاتورة،
حد التنبيه الافتراضي للمخزون، تفعيل تنبيهات المخزون، وحد تنبيه الدين.
تُحفَظ فعليًا، وتُقرأ فورًا في: ترويسة التطبيق (اسم المتجر)، الفواتير
المطبوعة (اسم/هاتف/عنوان المتجر + بادئة الترقيم)، ولوحة التحكم.

### 3. الفواتير الاحترافية — ترقيم، طباعة، QR، تصدير PNG

- **ترقيم فريد وآمن**: نموذج `Counter` جديد يُحجز رقمًا تسلسليًا
  (`INV-000123`) داخل نفس معاملة إنشاء الفاتورة، فلا يمكن لعمليتي بيع
  متزامنتين الحصول على نفس الرقم.
- **صفحة عرض/طباعة** (`/sales/:id`): اسم المتجر، رقم الفاتورة،
  التاريخ والوقت، الزبون، المنتجات والكميات والأسعار، الإجمالي،
  المدفوع، المتبقي، وتوضيح صريح "نقدي" أو "دين".
- **QR Code** حقيقي (مكتبة `qrcode`) يحتوي رقم الفاتورة والإجمالي
  والتاريخ.
- **تصدير PNG** حقيقي (مكتبة `html2canvas`) و **طباعة** حقيقية (CSS
  مخصص يطبع الفاتورة فقط بدون بقية واجهة التطبيق).
- **إلغاء فاتورة**: `POST /api/sales/:id/cancel` — يُرجع الكمية
  المباعة إلى المخزون تلقائيًا (حركة `IN`/`RETURN`)، ويستبعد الفاتورة
  فورًا من كل الحسابات المالية (لأن كل تجميع مالي في النظام يفلتر
  `status: CONFIRMED` الآن) دون حذف السجل نفسه — يبقى محفوظًا بحالة
  "ملغاة" لأغراض التدقيق.

### 4. بدء يوم جديد (Start New Day) — آمن بالكامل

نموذج `DailyClosing` جديد يحفظ **لقطة فقط** (المبيعات، الربح، رصيد
الصندوق عند الإغلاق) — لا يُحذف أو يُعدَّل أي بيع أو مخزون أو دين إطلاقًا.
الآلية: "اليوم" في لوحة التحكم يبدأ من منتصف الليل، أو من وقت آخر إغلاق
إن حدث اليوم بالفعل، أيهما أحدث. زر "بدء يوم جديد" في لوحة التحكم يأخذ
هذه اللقطة، وسجل كل الإغلاقات السابقة يظهر أسفل اللوحة.

### 5. منطق المبيعات والديون — تمت المراجعة والتصحيح

- ✅ البيع النقدي يدخل مبيعات اليوم والنقد فورًا (`Invoice.paidAmount`
  يُحتسب في الصندوق).
- ✅ البيع بالدين يظهر في ديون الزبون (`remainingAmount`) ولا يزيد
  النقد الموجود إلا بمقدار المدفوع فعليًا.
- ✅ تسديد الدين يزيد النقد الموجود (`CustomerPayment` يُحتسب في
  الصندوق).
- ✅ المخزون ينقص عند البيع (كان موجودًا مسبقًا).
- ✅ **جديد**: إلغاء البيع يعكس تأثيره على المخزون (استرجاع الكمية)
  والحسابات (استبعاد فوري من المبيعات/الصندوق/الديون).
- ✅ كل عملية (بيع، إلغاء، دفعة، إغلاق يوم) تُسجَّل في `AuditLog`.

### 6. حساب الربح — مبني على تكلفة كل منتج فعليًا (COGS)

قبل: الربح = المبيعات − تكلفة شراء الحليب الإجمالية (غير دقيق، لا
علاقة مباشرة بما بيع فعليًا). الآن: كل صنف في الفاتورة يحفظ `unitCost`
(نسخة من `Product.costPrice` **لحظة البيع نفسه**، فلا يتأثر الربح
التاريخي بتغيّر التكلفة لاحقًا)، والربح = المبيعات − مجموع
(`unitCost × الكمية`) لكل الأصناف المباعة فعليًا − المصاريف. تكلفة
شراء الحليب ما زالت معروضة، لكن كرقم معلوماتي منفصل، لا تُطرَح مرتين.

**ربط الإنتاج بالتكلفة تلقائيًا**: عند تسجيل دفعة إنتاج فيها كمية حليب
مستهلكة، يُحسب متوسط سعر الحليب (من آخر 20 عملية شراء، مرجَّح بالكمية)
ويُحدَّث `Product.costPrice` تلقائيًا = (الحليب المستهلك × متوسط
السعر) ÷ الكمية المنتَجة. هذا يحقق السلسلة كاملة: **شراء الحليب →
المورد → الإنتاج → تكلفة المنتج → الربح**، بدون أي خطوة يدوية.

### 7. البحث الموحّد (Smart Search)

شريط بحث في أعلى كل صفحة (`apps/frontend/src/components/search/SmartSearchBar.tsx`)
متصل بـ `GET /api/search?q=` الذي يبحث فعليًا في: الزبائن (بالاسم أو
الهاتف)، الموردين، المنتجات، الفواتير (برقم الفاتورة أو اسم الزبون)،
ومشتريات الحليب (باسم المورد) — كل نتيجة قابلة للنقر وتنقل مباشرة
للعنصر المطلوب.

### 8. التقارير — تصحيح الربح + فلاتر سريعة

تقارير المبيعات/المشتريات/الديون كانت تستخدم بيانات حقيقية مسبقًا
(المرحلة 7). ما أُضيف الآن: فلترة الفواتير الملغاة من كل الحسابات،
عرض تكلفة البضاعة المباعة (COGS) الفعلية بدل تكلفة شراء الحليب، تنبيه
واضح إن وُجدت أصناف مباعة بلا سعر تكلفة مسجَّل، وأزرار فلترة سريعة
(اليوم / هذا الأسبوع / هذا الشهر) بجانب اختيار فترة مخصصة والتصدير
الموجود مسبقًا.

### 9. فحص الاتساق النهائي

راجعت يدويًا: كل الصلاحيات الـ 40 المعرَّفة مقابل ما هو مُطبَّق فعليًا
في الـ routes (تطابق تام باستثناء فجوة `manage_users` القديمة الموثّقة
أعلاه)، كل رابط في القائمة الجانبية مقابل Routes حقيقية (تطابق تام، لا
صفحات "قريبًا" متبقية — حُذف `ComingSoonPage.tsx` و `SettingsPlaceholder.tsx`
نهائيًا)، كل الـ 20 موديول Backend مُركَّبة في `app.ts`، وكل الـ 23
نموذج Prisma بعلاقات متسقة (لا علاقة تشير لنموذج غير موجود).

### قيود حقيقية معروفة (Final Polish)

- **لم يُشغَّل `pnpm install` أو `pnpm build` فعليًا** في بيئة كتابة
  هذا الكود (بدون إنترنت) — راجع الملاحظة أعلى هذا الملف. المراجعة
  كانت يدوية وشاملة (تتبع كل استيراد ونوع بيانات وعلاقة)، لكنها ليست
  بديلاً عن تشغيل المُصرِّف الفعلي.
- عملة الفاتورة حقل حر (يُفترض أن يكون رمز ISO مثل USD)؛ رمز غير صالح
  قد يسبب خطأ تنسيق عند العرض — أُضيفت ملاحظة توضيحية في نموذج الإعدادات
  لتقليل هذا الاحتمال.
- البحث الموحّد يتطلب صلاحية واحدة (`use_search`) للوصول لكل الأنواع
  معًا، بدل صلاحية منفصلة لكل نوع — تبسيط مقصود مناسب لحجم فريق العمل
  المتوقع لهذا التطبيق.

## إصلاح: المساعد الذكي وطباعة الفاتورة

مشكلتان اكتُشفتا أثناء الاختبار الفعلي بعد تسليم "تنظيف بيانات التشغيل".

### 1) المساعد الذكي يعرض خطأ ولا يعمل

**السبب الفعلي**: حالة "المفتاح غير موجود إطلاقاً" (`ANTHROPIC_API_KEY`
فارغ أو غير معرَّف) كانت **مُعالَجة بشكل صحيح أصلاً** — `getClient()`
في `assistant.service.ts` كانت ترمي رسالة عربية واضحة قبل هذا الإصلاح
أيضاً. **لكن** لم يكن هناك أي معالجة لفشل *استدعاء* Anthropic API نفسه
بعد تجاوز هذا الفحص — أي خطأ من مزوّد الذكاء الاصطناعي (مفتاح API
موجود لكنه خاطئ/منتهي، تجاوز الحد المسموح للطلبات، انقطاع اتصال
بالإنترنت من الخادم، أو اسم نموذج (`ASSISTANT_MODEL`) غير صحيح) كان
يمر بدون أي `catch`، فيصل كخطأ JavaScript خام إلى `errorMiddleware`
العام، الذي يحوّل أي خطأ غير متوقَّع إلى رسالة عامة غامضة — هذا الغموض
هو على الأغلب ما ظهر أثناء اختبارك.

**الإصلاح**: أُضيفت دالة `mapAnthropicError()` في
`apps/backend/src/modules/assistant/assistant.service.ts` تلتقط فشل
استدعاء `client.messages.create()` وتترجمه لرسالة عربية محدَّدة وكود
خطأ (`errorCode`) خاص بكل حالة:

| الحالة | errorCode | الرسالة |
|---|---|---|
| المفتاح غير موجود إطلاقاً | `ASSISTANT_NOT_CONFIGURED` | أضف ANTHROPIC_API_KEY في إعدادات الخادم |
| المفتاح خاطئ/منتهي | `ASSISTANT_INVALID_API_KEY` | تحقّق من المفتاح في إعدادات الخادم |
| تجاوز حد الطلبات | `ASSISTANT_RATE_LIMITED` | حاول مرة أخرى بعد قليل |
| النموذج غير موجود | `ASSISTANT_MODEL_NOT_FOUND` | تحقّق من ASSISTANT_MODEL |
| فشل اتصال الشبكة | `ASSISTANT_CONNECTION_FAILED` | تحقّق من اتصال الإنترنت في الخادم |
| أي خطأ آخر من الخدمة | `ASSISTANT_API_ERROR` / `ASSISTANT_UNKNOWN_ERROR` | حاول لاحقاً |

الواجهة الأمامية (`AssistantPage.tsx`) لم تحتَج أي تعديل — كانت أصلاً
تعرض `err.message` القادمة من الخادم لأي خطأ غير `ASSISTANT_NOT_CONFIGURED`،
وهذه الرسالة أصبحت الآن دائماً واضحة ومحدَّدة بدل نص عام.

**لم تُوضَع أي API key حقيقية في الكود أو المستودع** — لا تزال تُقرأ
حصراً من `process.env.ANTHROPIC_API_KEY` (متغيّر بيئة، موثَّق في
`.env.example`)، ولا يوجد أي تغيير على طريقة تخزينها أو قراءتها، فقط
على طريقة معالجة فشلها.

### 2) طباعة الفاتورة لا تعمل

**السبب الفعلي**: كانت `globals.css` تستخدم تقنية شائعة لكنها هشّة:
إخفاء كل عناصر الصفحة (`body * { visibility: hidden }`) ثم محاولة
"إخراج" بطاقة الفاتورة من هذا الإخفاء عبر
`#printable-invoice { visibility: visible; position: absolute; inset: 0; }`.
هذه التقنية تعمل **فقط** إذا كانت كل العناصر الأب لبطاقة الفاتورة
بدون أي تموضع خاص (position: static) — لكن هيكل التطبيق الفعلي
(`AppLayout.tsx`) يضع الفاتورة داخل حاويات `overflow-hidden` و
`overflow-y-auto` (مخصَّصة للتمرير على الشاشة)، وهذا معروف بأنه يكسر
حساب `position: absolute` في متصفحات Chrome/Edge بشكل غير متوقَّع —
فتظهر معاينة الطباعة فارغة أو مقصوصة أو بعرض خاطئ (`max-w-lg` كان
يبقى فعّالاً أيضاً، فيحصر عرض الفاتورة بـ 512px بدل عرض الصفحة كاملاً).

**الإصلاح**: استُبدلت التقنية بالكامل بالطريقة الأكثر موثوقية والمُتَّبعة
فعلياً في أغلب التطبيقات الحقيقية — إخفاء مباشر (`display: none`) لعناصر
واجهة التطبيق نفسها بدل محاولة "الهروب" من إخفاء عام:

- `apps/frontend/src/layouts/Header.tsx` و `Sidebar.tsx`: أُضيفت فئة
  `no-print` مباشرة على العنصر الجذر لكل منهما.
- `apps/frontend/src/layouts/AppLayout.tsx`: أُضيفت فئتا `app-shell`
  و `app-body` على حاويات التخطيط الرئيسية ليمكن استهدافهما بدقة.
- `apps/frontend/src/styles/globals.css`: قاعدة `@media print` الجديدة
  تُخفي `.no-print` بـ `display: none !important` (إزالة كاملة من
  الشجرة، بلا أي تلاعب بالتموضع)، وتُعيد ضبط قيود الارتفاع/التمرير
  الخاصة بالشاشة (`h-screen`, `overflow-hidden`, `overflow-y-auto`)
  إلى `auto`/`visible` حتى تتدفق الفاتورة بشكل طبيعي على صفحة الطباعة،
  وتُلغي `max-width` عن `#printable-invoice` لتستخدم العرض الكامل.
- لم يتغيّر شيء في `InvoiceViewPage.tsx` نفسها — لا في منطق QR ولا في
  تصدير PNG ولا في زر الطباعة (`window.print()` نفسه، بلا أي iframe أو
  popup أو خدمة خارجية، كما طُلب).

### الاختبار الفعلي (وليس "الميزة موجودة في الكود")

بيئة العمل بدون إنترنت (لا يمكن تشغيل متصفح حقيقي أو تثبيت حزم npm)،
فاستُخدمت أدوات Node.js المدمجة (v22) لتنفيذ اختبارات حقيقية فعلية:

1. **المساعد الذكي**: أُعيد بناء تسلسل الأصناف الفعلي لأخطاء SDK
   (`APIConnectionError`, `AuthenticationError`, `RateLimitError`,
   `NotFoundError`, `APIError` — بنفس التوريث الحقيقي) وتشغيل
   `mapAnthropicError()` **الحقيقية المنسوخة من الكود نفسه** ضد الستة
   حالات كلها — **نجحت كل الحالات الست**.
2. **مسار المفتاح المفقود كاملاً عبر HTTP حقيقي**: تشغيل خادم
   `http.createServer` حقيقي يطبّق `AppError`/`sendError` المنسوخين
   حرفياً من الكود، واستدعاؤه عبر `fetch()` حقيقي (وليس محاكاة) يطبّق
   منطق `apiClient.ts` و `AssistantPage.tsx` حرفياً — تأكَّد أن ما يصل
   فعلياً للمستخدم هو الرسالة العربية الواضحة، وليس نص غامض.
3. **الطباعة**: فحص برمجي (Node) طابق كل انتقاء CSS في `globals.css`
   ضد الفئات الفعلية الموجودة في `Header.tsx`, `Sidebar.tsx`,
   `AppLayout.tsx`, `InvoiceViewPage.tsx` — تأكَّد أن التقنية الهشّة
   القديمة (`visibility:hidden` + `position:absolute`) أُزيلت بالكامل،
   وأن كل فئة تعتمد عليها CSS الجديدة (`no-print`, `app-shell`,
   `app-body`, `printable-invoice`) موجودة فعلاً في مكانها الصحيح، وأن
   صورة QR تقع داخل `#printable-invoice` (تُطبَع) وليست خلف `no-print`
   (لا تُخفى بالخطأ).
4. **اختبارات Backend جديدة**: `assistant.chat.test.ts` — يغطي مسار
   المفتاح المفقود، والمفتاح الفارغ (`ANTHROPIC_API_KEY=""`)، وكل حالات
   خطأ SDK الخمس، وحالة النجاح العادية — عبر محاكاة كاملة لـ
   `@anthropic-ai/sdk` (نفس بنية توريث الأخطاء الحقيقية).
5. **إعادة فحص شامل**: لم تتأثر أي وحدة أخرى — `assistant.tools.ts`
